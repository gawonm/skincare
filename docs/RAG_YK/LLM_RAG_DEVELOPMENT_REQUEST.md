# 개발 요청서: 채팅방 세션을 사용하는 LangGraph LLM·RAG 프레임

작성일: 2026-09-09

이 문서는 개발자 또는 코딩 에이전트에게 전달하는 구현 요청서다. 구현 대상은 LLM·RAG 담당 영역의 실행 프레임이며, DB·제품 데이터·운영 환경의 최종 선택을 요청하는 문서가 아니다.

## 1. 요청

기초화장품 추천·사용 계획 서비스를 위한 **LangGraph 기반 LLM·RAG 실행 프레임**을 구현해 주세요. 실제 DB나 완성된 데이터셋이 없어도 개발용 데이터와 가짜 모델로 분기·검색·멀티턴·세션 복원·오류 처리를 실행할 수 있어야 합니다. 이후 저장소와 실제 모델을 연결할 때 그래프의 주요 흐름을 바꾸지 않도록 연동 지점을 분리해 주세요.

프로젝트 문맥은 [LLM·RAG 파이프라인](LLM_RAG_PIPELINE.md)과 [프로젝트 재정의](PROJECT_REDEFINITION.md)를 참고합니다. 이번 구현 범위와 충돌하는 이전 제안은 이 요청서의 범위를 따릅니다. DB·백엔드와 연결할 세부 계약은 [DB·히스토리 연동 요청서](LLM_RAG_DB_CONTRACT.md)에 있습니다.

## 2. 확정 사항과 미정 사항

### 확정

- 담당 영역은 LLM·RAG다. LangGraph의 `StateGraph`로 실행 흐름과 상태를 명시한다.
- 서비스는 채팅방별 세션을 갖는다. 같은 방에서 이어지는 질문은 맥락을 유지하고 다른 방과는 격리한다.
- 상품 탐색·추천, 루틴 생성·수정, 성분·병용 설명의 세 가지 Intent를 지원한다.
- 한 입력의 복합 목적, 앞선 후보 참조, 기존 조건 수정, 필요한 경우의 추가 질문을 지원한다.
- 추가 질문 뒤에는 실행을 종료한다. 답변을 기다리는 동안 HTTP 요청이나 그래프 실행을 계속 붙잡지 않는다.
- 이번에는 전체 프레임을 구현한다. 기능이 없는 인터페이스 선언만으로 끝내지 않고 개발용 구현을 연결해 끝까지 실행한다.

### 미정 또는 이번 범위 밖

- 관계형 DB·문서 DB·벡터 저장소·그래프 DB·운영 체크포인터의 제품 및 물리 스키마
- LLM 공급자·모델, 임베딩 모델, 운영 배포 방식
- 실제 상품 추천 품질을 위한 대규모 데이터 구축·수집·학습
- 전문적인 루틴 최적화 알고리즘 및 새로운 임상 사용 규칙 작성
- 프론트엔드 채팅 UI, 회원·로그인 구현, 운영용 DB 서버 구축
- 구매 예산 입력, 가격 선호 온보딩, 가격 기반 개인화 정책
- 전체 Hetionet·MedDRA 구축 및 필수 경유 경로

Python 프로젝트의 현재 설정은 `pyproject.toml`을 먼저 확인한다. 작성 시점에는 Python `>=3.14`와 기존 KG 튜토리얼 패키지가 있다. 호환되는 LangGraph 의존성을 확인해 기록하고, 기존 패키지와 실행 경로를 보존한다. Python 최소 버전을 이유 없이 낮추거나 기존 프로젝트 전체를 교체하지 않는다.

## 3. 용어 정정: 내부 실행 제한과 멀티턴

이전 흐름도의 '예산 남음'은 **한 사용자 턴에서의 내부 도구 호출·재검색·수정 제한 미도달**로 바꾼다. 사용자 구매 예산과 관계없다.

- `execution_limits`: 운영 설정. 최대 도구 호출 수, 최대 수정 횟수, 요청 실행 시간, LangGraph 재귀 제한 등을 관리한다.
- `context_limits`: 모델에 보낼 컨텍스트 길이 설정. 실행 반복 횟수와 구분한다.
- 멀티턴: 사용자 메시지가 새로 도착해 같은 채팅방에서 다음 실행을 시작하는 것.
- 내부 반복: 한 메시지를 처리하는 동안 시스템이 재검색·재검증하는 것.

제한에 도달하면 `partial` 또는 설명 가능한 오류로 종료한다. 실제 도구 호출에도 타임아웃을 적용하고, 매 루프 진입 전에 실행 제한을 확인한다. 그래프 재귀 제한을 유일한 종료 장치로 사용하지 않는다. 새 사용자 요청에서는 실행 카운터를 초기화하되 기존 방의 프로필·후보·질문·계획은 유지한다. 같은 요청의 네트워크 재시도는 새 사용자 턴으로 세지 않는다.

구매 예산 필드나 질문을 이번 스키마에 기본 포함하지 않는다. 가격 관련 요구가 입력되어 현재 구현에서 처리할 수 없으면 미지원 조건으로 표시한다. 이를 충족했다고 답하거나 조용히 무시하지 않는다.

## 4. 구현할 책임 경계

| 구성 | 이번에 구현할 내용 |
| --- | --- |
| `ChatService` | 검증된 채팅방 범위, 중복 요청 처리, 히스토리 계약 호출, 그래프 실행과 응답 저장 조정 |
| LangGraph | 상태, 노드, 조건 분기, 대기 질문, 내부 반복 종료, 결과 구성 |
| LLM 계층 | 구조화된 출력 계약, 공급자 교체 지점, 테스트용 `FakeLLM` |
| RAG 계층 | 검색 요청 작성, `Retriever` 호출, 결과·출처·조건 처리, 무결과/오류 구분 |
| 제품·성분 접근 | 조회 계약과 인메모리/로컬 fixture 구현 |
| 계획 접근 | `RoutinePlanner` 계약, 테스트용 최소 계획 생성·검증 구현 |
| 세션·히스토리 | 조회·저장 계약과 인메모리 구현, LangGraph 체크포인터 주입 |
| 컨텍스트 구성 | 현재 상태·최근 메시지·필요한 요약·검색 근거를 제한된 길이로 구성 |
| 검증·관찰 | 스키마·참조·근거·계획 검증, 노드·도구·실행 시간·종료 사유 기록 |

실제 DB 어댑터, 검색 색인 구축, 고도화된 스케줄러는 교체 가능한 경계로 둔다. 도메인 데이터 접근 노드 안에 특정 DB 클라이언트를 직접 생성하지 않는다. 최초 실행은 네트워크·유료 API 키 없이 가능해야 한다. 테스트용 가짜 모델은 정해진 시나리오의 분류/출력을 제공하는 용도이며 실제 자연어 성능을 입증하지 않는다.

## 5. 입력·출력 계약

HTTP 경로를 먼저 확정할 필요는 없다. UI나 서버에서 호출할 수 있는 비동기 서비스 진입점과 구조화된 DTO를 먼저 만든다.

### 입력 `ChatTurnInput`

- `chat_room_id`: 접근 권한이 확인된 채팅방 식별자
- `request_id`: 재전송해도 유지되는 요청 식별자
- `message`: 이번 사용자 메시지
- 선택적인 명시적 참조: `candidate_set_id`, `routine_version`

인증된 사용자 정보는 서버가 검증한 별도 컨텍스트로 주입한다. 클라이언트가 본문에 넣은 사용자 ID나 임의 `thread_id`를 권한의 근거로 신뢰하지 않는다. 클라이언트가 전체 대화 원문을 매번 보내는 것을 전제로 삼지 않는다.

### 출력 `ChatTurnOutput`

- `chat_room_id`, `request_id`, `assistant_message_id`
- `status`: `completed | needs_input | partial | error`
- `message`: 사용자에게 표시할 답변
- `intents`: 실행한 목적 목록
- `follow_up_question`: 필요한 경우만 제공
- `artifacts`: 후보 목록, 루틴 초안/수정, 비교 결과 등 구조화된 결과
- `citations`: 근거 ID, 출처 ID, 확인 가능한 원문 위치
- `unresolved`: 누락 정보·미지원 조건·근거 부족·상충
- `error_code`, `retryable`: 오류인 경우 제공

사용자 질문 대기를 뜻하는 `needs_input`은 이번 실행이 정상적으로 끝난 결과다. 백엔드의 요청 처리 상태는 완료로 저장하고 다음 사용자 답변은 새 `request_id`로 처리한다. 내부 실행 흔적과 전체 도구 출력은 사용자 답변에 그대로 포함하지 않는다.

## 6. LangGraph 상태와 노드

상태는 지속되는 세션 정보와 이번 요청의 임시 정보를 구분한다.

| 유지되는 상태 | 이번 요청마다 갱신할 상태 |
| --- | --- |
| 메시지 맥락·요약, 사용자 제공 조건, 대기 질문 | 이번 메시지·의도·작업 목록 |
| 보유 제품·선택 제품·후보 목록과 표시 순서 | 검색 요청·현재 검색 결과·검증 결과 |
| 현재 루틴과 버전, 값의 출처 | 호출·수정 횟수, 타임아웃 정보, 현재 오류 |
| 결과를 설명하는 근거 참조 | 현재 응답 DTO |

LLM 출력의 Intent·조건·참조는 스키마로 검증한다. 출처가 다른 값은 구분하고, 사용자 수정이 이전 가정보다 우선하게 한다. 미공개 농도·pH는 미상으로 남긴다. 제품 후보와 실제 보유 제품은 별도 필드로 관리한다.

추천 노드는 다음과 같으며 동등한 역할로 이름을 조정할 수 있다.

```text
ChatService: 권한 확인 → 요청 등록/중복 검사 → 방 상태 복원
  START
  → prepare_turn                 # 이번 실행 필드 초기화·중복 없는 신규 입력 반영
  → understand_request           # 목적·조건·참조·변경 추출
  → resolve_entities             # 성분·제품 식별
  → assess_information           # 진행 가능 / 조회로 보완 / 사용자 질문
      → lookup_information → assess_information
      → ask_user → finalize_response → END
      → route_task
          → discover_products
          → plan_routine
          → answer_evidence_question
  → validate_result
      → 제한 안에서 필요한 검색/작업 재실행
      → finalize_response → END
ChatService: 결과·히스토리·세션 스냅샷 저장 → 응답 반환
```

각 작업이 필요한 때 공통 `retrieve_evidence`와 `assess_applicability`를 호출하도록 한다. 순수 상품 조건 조회에 문헌 검색을 강제하지 않는다. 복합 요청은 작업 목록을 순차 소비하며 추천 후보 전체를 동시에 일정에 넣지 않는다.

### 질문 후 이어가기

`ask_user`는 필요한 질문 1~2개와 `pending_question`을 저장하고 `END`로 종료한다. 같은 방의 다음 메시지를 실행할 때 대기 질문과 함께 해석한다. 사용자가 질문에 답하지 않고 다른 작업을 요청하면 이전 대기를 무조건 강제하지 않고 해소·대체 여부를 판단한다.

기본 채팅 멀티턴에는 `interrupt()`를 필수로 사용하지 않는다. 이번 범위는 정상 종료 후 새 입력을 받는 형태다. 향후 실행 중 사람의 승인이 꼭 필요한 별도 작업에 interrupt/resume 계약을 추가할 수 있다. [LangGraph interrupt 문서](https://docs.langchain.com/oss/python/langgraph/interrupts)

## 7. 채팅방 상태와 히스토리 처리

**대화 원문, 체크포인트, LLM 입력 컨텍스트를 구분한다.**

1. 대화 원문: 사용자에게 보여줄 메시지와 구조화된 응답의 공식 기록. 백엔드 히스토리 계약으로 저장한다.
2. 체크포인트: LangGraph가 방별로 이어갈 실행 상태. 그래프 생성 시 외부에서 체크포인터를 주입한다.
3. LLM 컨텍스트: 요약, 최근 대화, 대기 질문, 관련 후보·계획·검색 근거를 이번 호출에 맞게 구성한 임시 입력이다.

접근 권한이 확인된 채팅방을 안정적인 `thread_id`로 연결한다. 같은 사용자라도 다른 방은 다른 thread이고, 브라우저 새로고침·재접속은 같은 방의 thread를 유지한다. 개발에서는 애플리케이션 수명 동안 하나의 `InMemorySaver`를 재사용한다. 매 요청마다 새로 생성하지 않는다. 프로세스 재시작 후 데이터 보존은 운영 체크포인터 연결 전에는 보장하지 않는다. [LangGraph persistence](https://docs.langchain.com/oss/python/langgraph/persistence)

체크포인트가 있으면 기존 상태를 복원하고 신규 메시지/변경만 전달한다. 전체 DB 히스토리와 체크포인트 메시지를 매번 합쳐 넣지 않는다. 메시지 ID와 메시지 reducer의 동작을 확인하고 `add_messages` 등을 사용해 중복과 덮어쓰기 정책을 명확히 한다. 매 요청에 빈 프로필·빈 후보·빈 계획을 넣어 이전 상태를 초기화하지 않는다. [Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

체크포인트가 없지만 백엔드에 히스토리가 있으면 마지막으로 커밋된 세션 스냅샷, 후보·계획 결과, 필요한 최근 대화를 이용해 세션을 재구성한다. 원문만 있고 구조화된 후보 목록을 복구할 수 없다면 '2번'을 추측하지 않고 확인한다. 재구성은 완료된 턴의 대화 연속성을 복구하는 것이며 실행 중이던 노드의 정확한 재개와는 다르다.

긴 대화에서는 요약과 최근 대화를 함께 사용한다. 요약에는 해당 채팅방, 버전, 포함 범위를 나타내는 메시지 순번을 기록한다. 요약 범위와 최근 메시지 범위를 겹쳐 중복 주입하지 않는다. 요약 때문에 원문을 삭제하지 않는다. 명시적 사용자 수정, 대기 질문, 현재 후보의 번호·ID, 계획 버전은 서술형 요약에만 맡기지 않고 구조화 상태로 유지한다. 도구 호출 메시지를 모델에 전달한다면 호출과 응답의 쌍을 보존한다. [LangGraph memory](https://docs.langchain.com/oss/python/langgraph/add-memory)

다른 방의 프로필이나 장기 메모리는 자동으로 가져오지 않는다. 방을 넘는 사용자 공통 프로필은 별도 합의가 필요한 후속 기능이다. 사용자 대화 히스토리를 공용 문헌 검색 색인에 넣지 않는다.

## 8. DB가 미정일 때의 RAG 구현

`ProductRepository`, `IngredientRepository`, `EvidenceRetriever`, `RoutinePlanner`, `ChatHistoryRepository` 등의 계약과 개발용 구현을 분리한다. LangGraph 체크포인터는 공식 저장 인터페이스를 주입하며, 임의의 단순 `load/save` 함수가 체크포인터를 완전히 대체한다고 가정하지 않는다.

검색 결과는 적어도 근거 ID, 원문 구간, 출처, 문서 버전, 적용 조건, 검수 상태를 전달한다. 점수는 검색 관련도이며 안전성 확률이나 근거의 질로 쓰지 않는다. 조회 성공이지만 결과 없음과 도구 실패를 구분한다.

초기 retriever는 로컬 fixture의 키워드 검색 등으로 동작하게 해도 된다. 임베딩이나 벡터 저장소를 연결하지 않았다면 이를 하이브리드 검색 구현 완료라고 표시하지 않는다. Hetionet·그래프 탐색은 선택적 확장 인터페이스로 두고 기본 그래프 실행의 필수 의존성으로 만들지 않는다.

fixture 근거와 상품은 `is_demo` 또는 동등한 구분을 둔다. 가짜 논문 DOI·실제 연구처럼 보이는 출처를 만들어 넣지 않는다. 가짜 모델·샘플 규칙을 이용한 테스트가 통과해도 실제 제품 추천·병용 안전성 검증이 끝났다고 보고하지 않는다.

## 9. 백엔드 연동과 실패 처리

[DB·히스토리 연동 요청서](LLM_RAG_DB_CONTRACT.md)의 방 권한, 메시지 순서, 중복 요청, 결과 스냅샷, 동시성 계약을 구현체 없이도 테스트할 수 있게 한다.

- 동일 요청의 재전송은 사용자·assistant 메시지를 중복 생성하지 않는다.
- 같은 방의 두 요청이 동시에 상태를 덮어쓰지 않도록 첫 버전은 방별 순차 실행 또는 두 번째 요청의 명시적 충돌 반환을 사용한다.
- 다른 방의 요청은 독립 처리한다. 프로세스 전역의 단일 대화 상태를 사용하지 않는다.
- 사용자 메시지 저장 실패 시 그래프를 실행하지 않는다.
- 그래프 결과 생성 후 응답 저장이 실패하면 정상 저장 완료로 보고하지 않는다. 재시도 시 생성 결과 재사용 또는 완료된 스냅샷 기준 복구를 수행하며 중복 부작용을 막는다.
- 인메모리 잠금·저장소는 개발용이다. 다중 프로세스 동시성과 장애 후 복구를 해결했다고 주장하지 않는다.

외부 DB와 체크포인트 저장의 전체 원자성을 LangGraph가 자동으로 보장한다고 가정하지 않는다. 이번에는 실패 상태와 재시도 경계를 구현하고 운영 저장 방식은 백엔드와 협의한다.

## 10. 산출물과 검증

기존 패키지 구조에 맞는 위치에 새 모듈을 추가한다. `graph`, `state/schemas`, `nodes`, `prompts`, `ports`, `adapters`, `context`, `service` 책임을 구분하되 내용 없는 파일을 과도하게 만들지 않는다.

필수 산출물:

1. 실행 가능한 LangGraph와 채팅 서비스 진입점
2. 구조화된 입출력·상태·조회/저장 계약
3. `FakeLLM`, fixture 검색·상품·히스토리·계획 어댑터와 주입 가능한 체크포인터
4. 프롬프트 템플릿과 컨텍스트 구성·요약 정책
5. 테스트와 여러 채팅방을 사용하는 데모
6. 실행 방법, 실제 구현/대체 구현/미구현 구분, 향후 DB·모델 연결 위치를 설명한 문서
7. DB 담당자가 검토할 연동 계약의 변경 사항

핵심 테스트는 다음을 포함한다.

- 세 Intent와 복합 요청, 불필요한 질문 없는 단순 검색
- 질문 → `needs_input` 정상 종료 → 같은 방의 다음 입력에서 계속 처리
- '2번으로', '2번은 싫어', '월요일은 빼줘'의 참조·부정·수정
- 같은 방에서 상태 유지, 다른 방 격리, 잘못된 방 접근 차단
- 메시지 재전송 시 중복 없음, 같은 방 동시 요청의 명시적 처리
- 긴 대화 요약 뒤 후보 번호·제외 조건·대기 질문 유지
- 미공개 값·근거 없음·검색 실패 구분
- 내부 실행 제한 도달과 다음 새 요청의 카운터 초기화
- 응답 저장 실패 뒤 재시도, 체크포인트 미존재 시 커밋된 스냅샷으로 복구
- DB·벡터 서비스·유료 API 키 없이 데모 실행

먼저 저장소와 기존 지침을 확인하고 변경 범위를 짧게 설명한 뒤 구현해 주세요. DB 미정이라는 이유로 작업을 중단하지 말고 계약과 개발용 어댑터로 실행 프레임을 완성해 주세요. 검증 결과와 실제 연결이 남은 부분을 구분해 보고해 주세요.
