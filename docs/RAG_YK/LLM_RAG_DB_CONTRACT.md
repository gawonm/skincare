# 백엔드·DB 연동 요청서: 채팅방 히스토리와 RAG 접근 계약

작성일: 2026-09-09

상태: LLM·RAG 담당 영역에서 제안하는 논리적 연동 계약. DB 제품, 물리 테이블, 인덱스, HTTP 경로, 인증 구현은 확정하지 않는다. 요청서를 작성한 단계이며 다른 담당자에게 전송하거나 합의한 상태는 아니다.

연계 문서: [LangGraph 개발 요청서](LLM_RAG_DEVELOPMENT_REQUEST.md), [파이프라인 설계](LLM_RAG_PIPELINE.md).

## 1. 요청 목적과 역할

채팅방에 다시 들어왔을 때 이전 대화·추천 후보·대기 질문·사용 계획을 이어가고, 다른 방의 맥락은 섞이지 않도록 조회·저장 인터페이스를 제공해 주세요.

| 담당 | 책임 제안 |
| --- | --- |
| 서비스 백엔드·DB | 방 존재·접근 권한 확인, 메시지 순서·저장·페이지 조회, 요청 중복/동시성 처리, 완료 결과와 복구 스냅샷 보관 |
| LLM·RAG | 대화 해석, 요약·컨텍스트 구성, LangGraph 상태·노드, 후보·계획·근거 결과 생성, 저장 계약 호출 |
| 공동 결정 | 운영 체크포인터의 저장 방식·배포·수명, 재시도/복구 프로토콜, 버전 변경·보관 정책 |

상품 DB·문헌 검색 시스템과 대화 저장소는 역할이 다르다. 같은 DB를 사용할지는 미정이며 계약상 분리한다. LangGraph 체크포인터도 히스토리 테이블과 반드시 동일한 저장소일 필요는 없다.

## 2. 식별자와 방 격리

| 항목 | 의미 |
| --- | --- |
| 인증 주체 | 서버가 확인한 사용자. 입력 본문의 임의 사용자 ID와 구분 |
| `chat_room_id` | 대화 범위. 같은 방 재접속 시 유지 |
| `thread_id` | 검증된 방에 서버가 연결한 LangGraph 식별자 |
| `request_id` | 한 사용자 요청의 중복 방지 키. 재전송 시 유지 |
| `message_id` | 각 메시지의 안정적인 식별자 |
| `sequence` | 방 안에서 순서를 결정하는 서버 부여 값 |
| `candidate_set_id` | 특정 응답에 제시된 후보와 표시 순서의 식별자 |
| `routine_id/version` | 사용 계획과 변경 버전 |

최소 고유 범위는 방/소유 범위와 요청 ID의 조합으로 정한다. 사용자 ID만으로 LangGraph thread를 정하지 않으며 클라이언트가 임의로 다른 방의 thread를 지정하게 하지 않는다. 시간값만으로 메시지 순서를 결정하지 않는다.

예상 동작: 방 A의 '2번'은 방 A에서 보여준 후보에만 연결한다. 방 B에 후보가 없으면 방 A의 목록을 사용하지 않는다. 로그인 세션 갱신이나 브라우저 새로고침 때문에 기존 방의 대화 상태를 초기화하지 않는다.

## 3. 보관할 논리적 데이터

아래는 필드 요구사항이며 테이블 수를 의미하지 않는다.

### 대화 메시지

- 방 ID, 메시지 ID, 요청 ID, 역할, 본문, 순번, 작성 시각
- 처리 상태와 사용자에게 보이는 메시지 여부
- assistant 결과 DTO 및 관련 artifact ID
- 재전송 판단을 위한 입력 fingerprint 또는 동등한 일치 검사

사용자·assistant 대화가 화면 히스토리의 기준이다. 내부 도구 호출·디버깅 로그를 채팅 메시지로 자동 노출하지 않는다.

### 구조화된 결과와 세션 스냅샷

- 후보 목록: 후보 ID·제품 버전·표시 번호와 순서·출처 응답 ID
- 계획: 계획 ID·버전·배치·적용 제약·변경 사항
- 대기 질문: 질문 ID·대상 필드·대기 이유·원래 작업
- 방별 조건: 사용자 제공 값과 미상/가정/자료 조회의 구분
- 근거 참조: 근거·출처·문서 버전·적용성 상태
- `schema_version`, `source_revision`, 마지막 완료 요청 ID

스냅샷은 완료 결과에 대응하는 재구성 가능한 구조화 상태다. 별도 테이블을 강제하지 않고 응답 artifact와 함께 저장해도 된다. 이것은 그래프의 노드·실행 대기 정보를 포함하는 체크포인트의 완전한 대체물이 아니다.

### 대화 요약

- 방 ID, 요약 내용, 버전
- 요약이 포함하는 마지막 메시지 순번 `covered_through_sequence`
- 생성 시 기준 히스토리 revision, 생성 시각

요약은 LLM·RAG 모듈이 만들고 저장소는 보관·조회한다. 늦게 끝난 오래된 요약이 새 요약을 덮어쓰지 않도록 revision을 검사한다. 원문은 요약과 별개로 유지한다. 원문 수정/삭제 기능이 생기면 관련 요약·스냅샷·체크포인트의 무효화 규칙도 함께 정한다.

## 4. 히스토리 접근 계약 제안

언어별 interface/Protocol 또는 서비스 API로 구현할 수 있다. 아래 메서드는 작업 단위를 나타내며 실제 엔드포인트 이름은 협의 가능하다.

| 작업 | 입력 | 결과·보장 |
| --- | --- | --- |
| `get_authorized_room` | 인증 주체, 방 ID | 접근 가능한 방과 안정적인 thread 연결. 없거나 권한 없으면 명시적 오류 |
| `begin_turn` | 방, 요청 ID, 신규 메시지, 필요 시 기대 revision | 한 번만 사용자 메시지를 기록하고 실행권 확보. 신규/진행 중/이미 완료/충돌 구분 |
| `get_messages` | 방, `after_sequence` 또는 `before_sequence`, `limit` | 안정적인 순서와 페이지 커서, 다음 페이지 존재 여부. 요약/최근 대화 선택 가능 |
| `get_session_context` | 방 | 마지막 커밋된 스냅샷·요약·결과 참조·revision |
| `get_artifacts` | 방, 후보 목록 또는 계획 ID/버전 | 그 방에 속하는 구조화 결과와 원래 표시 순서 |
| `complete_turn` | 방, 요청 ID, 고정 assistant 메시지 ID, 결과 DTO, 스냅샷, 기대 revision | assistant 메시지·결과·스냅샷·요청 완료 상태를 논리적으로 함께 확정. 재호출은 같은 결과 반환 |
| `mark_turn_failed` | 방, 요청 ID, 오류 코드, 재시도 가능 여부 | 실패 상태 기록·실행권 해제. 이미 완료된 요청을 실패로 덮어쓰지 않음 |
| `save_summary` | 방, 요약, 포함 순번, 기대 revision | 요약 버전의 일관성 보장 |

`get_messages`의 커서 경계 포함 여부와 반환 순서는 구현 시 문서화한다. LLM 입력으로 구성할 때는 오름차순을 사용한다. 최근 N개 조회는 방별 순번을 기준으로 수행한다. 요약이 K번까지 포함하면 원문 문맥은 K번 이후를 사용해 중복을 줄인다.

`begin_turn`과 `complete_turn`은 백엔드 내부의 단일 트랜잭션 또는 동등한 일관성 보장으로 구현하는 것이 요구사항이다. 어떤 DB나 락 기술로 구현할지는 확정하지 않는다. 체크포인트 저장소까지 포함한 분산 트랜잭션을 요구하는 것은 아니다.

## 5. 정상 요청 처리 순서

1. 백엔드가 방 접근 권한과 thread 연결을 확인한다.
2. `begin_turn`으로 입력을 한 번 기록한다. 같은 키의 완료 결과가 있으면 바로 반환하고 LLM을 다시 호출하지 않는다. 같은 키에 다른 본문이 오면 충돌로 처리한다.
3. 같은 방은 순차 실행하거나 실행 중임을 반환한다. 서로 다른 방은 독립 처리한다.
4. LLM 서비스가 체크포인트를 복원한다. 신규 방은 초기화한다. 체크포인트가 없으면 마지막 커밋된 세션 스냅샷과 필요한 메시지로 복구한다.
5. 신규 메시지는 저장된 메시지 ID로 한 번만 반영한다. 정상 경로에서 전체 히스토리를 매번 체크포인트에 재추가하지 않는다.
6. 그래프가 응답을 생성한다. assistant 메시지 ID는 재시도해도 유지되는 값으로 정한다.
7. `complete_turn`으로 답변·후보·계획·대기 질문을 함께 저장한다. 저장 성공 후 완성된 응답을 반환한다.

이번 프레임은 완성 응답을 반환하는 방식으로 먼저 구현한다. 스트리밍을 추가한다면 전송 중 토큰과 최종 저장 완료를 구분하고, 저장 전 임시 출력을 확정된 히스토리로 표시하지 않는 계약을 추가한다.

`needs_input` 응답도 위 7단계에서 완료로 저장한다. 실행권을 유지한 채 다음 사용자 답변을 기다리지 않는다. 다음 답변은 같은 방의 새 요청이다.

## 6. 저장소 간 일관성과 복구

대화 원문·완료 요청 기록은 서비스 히스토리의 기준이다. 체크포인트는 진행 상태를 갖고, 커밋된 스냅샷은 완료된 세션을 재구성한다. 이 셋의 revision과 요청 ID가 어긋났을 때의 정책이 필요하다.

| 실패 위치 | 요구 동작 |
| --- | --- |
| 사용자 메시지 기록 전 | 그래프를 실행하지 않고 재시도 가능한 오류 반환 |
| 사용자 기록 후, 그래프 완료 전 | 같은 요청 ID로 재시도. 입력 중복 금지. 지원되는 체크포인트 복구 또는 마지막 커밋 상태에서 재실행 |
| 그래프 완료 후, 응답 저장 실패 | 해당 요청의 생성 결과가 남아 있으면 결과 저장만 재시도. 새 사용자 요청으로 처리하지 않음 |
| 응답 저장 완료 후, 네트워크 응답 유실 | 동일 요청 재전송에 저장된 결과 반환 |
| 체크포인트 유실, 히스토리 존재 | 마지막 커밋 스냅샷과 원문/결과로 재구성. 실행 중 노드의 정확한 복원이라고 표시하지 않음 |
| 스냅샷까지 부족 | 복구할 수 없는 후보·계획을 추측하지 않고 필요한 참조를 확인 |

그래프 결과가 남아 있는지 확인하려면 요청 ID·입력 fingerprint·결과 상태를 체크포인트와 완료 기록에서 대응시킬 수 있어야 한다. 앞선 요청이 미확정이면 다음 요청으로 그 상태를 덮어쓰지 않는다. 처리 중 요청의 만료·재실행권 획득은 운영 환경에서 별도 설계한다. 기본 인메모리 어댑터는 같은 프로세스의 재시도와 격리만 검증한다.

초기 그래프의 외부 조회는 읽기 중심이고, 자체 히스토리 저장은 중복에 안전해야 한다. 이후 외부 시스템을 변경하는 도구를 추가하면 그 도구도 독립적인 중복 방지 계약이 필요하다.

## 7. RAG·상품 조회 계약

| 인터페이스 | 요청 | 응답 |
| --- | --- | --- |
| `IngredientRepository.resolve` | 원문 성분명·언어 | 정규 성분 ID·정확한 형태·매핑 상태·모호한 후보 |
| `ProductRepository.search` | 카테고리·성분·제형 등 지원 조건 | 제품 ID·버전·조건에 해당하는 확인된 속성·페이지 정보 |
| `ProductRepository.get` | 제품 ID·버전 | 전성분·공개 농도·사용법·출처·확인일 |
| `EvidenceRetriever.search` | 검색문·성분/제품 ID·사용 조건·검색 개수 | 근거·원문·조건·검수 상태·검색 메타데이터 |
| 선택적 `EvidenceGraph.lookup` | 제품/성분/근거 ID | 연결된 근거 ID·관계·출처 |

문헌 검색 결과는 최소 `evidence_id`, `source_id`, `document_version`, `text`, `locator`, `conditions`, `review_status`를 갖는다. 존재하면 URL/DOI도 포함한다. 모든 성분/제품에 모든 조건이 있을 필요는 없으며 누락 값은 명시적으로 표현한다.

빈 검색 결과, 지원되지 않는 필터, 데이터 없음, 접근 불가, 타임아웃을 구분한다. 검색 개수와 관계없는 임의 결과를 반환해 성공으로 표시하지 않는다. 구매 예산·가격 필터는 이번 확정 계약에 포함하지 않는다. 서버가 지원하지 않는 조건은 미지원으로 돌려준다.

실제 저장소와 색인을 선택하기 전에는 작은 로컬 fixture로 계약을 구현한다. 데모 데이터의 출처와 상태를 표시하며, 실제 DB 연동·벡터 검색·임상 근거 검증이 완료된 것처럼 표현하지 않는다.

## 8. 백엔드 담당자와 최종 합의할 항목

아래 항목은 실제 운영 연결 전에 결정하면 되며 LLM·RAG 프레임 구현의 선행 차단 조건은 아니다.

- 방 생성·권한 확인 결과의 전달 방식과 식별자 범위
- 방별 메시지 순번, 페이지 커서와 revision 의미
- `begin_turn`/`complete_turn`에 해당하는 저장 작업의 담당 서비스
- 운영 체크포인터의 저장소·프로세스 배치·연결 수명
- 동시 요청을 큐에 넣을지 충돌로 반환할지, 처리 중 요청 복구 방식
- 히스토리·요약·결과 스냅샷·체크포인트의 보관/삭제와 버전 전환 방식
- 상품·성분·문헌 조회 서비스의 DTO, 미상 값과 오류 코드

채팅방을 넘는 사용자 공통 프로필과 구매 예산 입력은 별도 기획 사항으로 남긴다.
