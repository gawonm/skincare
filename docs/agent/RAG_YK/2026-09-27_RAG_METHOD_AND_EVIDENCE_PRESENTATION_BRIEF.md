# 발표에 사용할 RAG 설명

> 아래는 발표 본문용이다. 실험 과정·이전 검토와 세부 수치는 하단의 **기존 검토 기록**에 보존했다. 기준일 2026-09-27.

## 한 문장으로 설명

피부 고민과 현재 상태에 맞는 **NIA 유사 사례를 탐색**하고, 사례 속 성분 주장을 원문과 연결한 뒤 별도의 근거 검증과 제품·루틴 단계로 넘기는 RAG를 설계했다. NIA 사례는 검증된 효능 근거가 아니라 탐색 자료다. 최종 목표는 사례 검색 점수가 아니라 **사용자의 복합 요청을 충족하는 실행 가능한 설명**이다.

## 왜 지금 이 방식을 쓰는가

| 결정 | 선택 근거 | 발표에서 말할 범위 |
| --- | --- | --- |
| Case 단일 질의: 완성형은 원문, 첫 턴 키워드형은 제한적 LLM 정리 | 자유형 LLM 재작성은 기존의 충분히 서술된 24개 개발 질의에서 Dense 후보 qrel Recall@40을 **0.648→0.617**로 낮췄다. | 완성형은 원문과 조건을 보존한다. 새 키워드형 경로는 기존 intent 해석 LLM의 초안을 쓰되 검출 가능한 연령·피부타입·고민·부위·성분이 추가되면 원문으로 돌아간다. 키워드형 경로의 검색 성능 수치는 아직 없다. |
| BGE-M3 Dense Top-40 → BGE 재정렬 → Top-3 | 현재 Claim 추출에는 최대 3개 사례를 넘긴다. Dense40의 관련 사례 Hit@3는 **22/24**, 등급 3 Hit@3는 **17/24**였다. | 리랭커의 목적은 관련 사례를 포함시키는 것이다. 상위 사례의 순서를 반영하는 nDCG는 보조 지표다. |
| Case용 Hybrid·Top-5 운영 도입 보류 | 동일 예산 Hybrid40과 후보 48건 Hybrid48은 후보 회수율은 높였지만, 최종 Hit@5는 Dense40과 모두 **22/24**, 등급 3 Hit@5도 모두 **19/24**였다. 평균 관련 사례 수@5는 Dense40 **3.667**, Hybrid48 **3.750**으로 소폭 차이다. | 이 개발셋과 현재 전달 예산에서는 추가 검색 복잡도나 Top-5 계약 변경을 정당화할 최종 포함률 이득이 확인되지 않았다. |

위 수치는 **동일한 24개 반복 개발·회귀 질의**에서 나온 Case 검색 비교다. `Hit@K`는 상위 K개에 등급 2~3 사례가 한 건 이상 포함된 질의의 비율이다. `등급 3 Hit@K`는 더 강한 관련 사례의 포함률이고, `평균 관련 사례 수@K`는 K개 안에 담긴 관련 사례의 평균 개수다. 후보 `qrel Recall@40`은 판정한 관련 사례 중 1차 후보에 든 비율이며 전체 코퍼스의 완전 Recall이 아니다. ## 발표에서 보여줄 흐름과 현재 결론

1. **역할:** 유사 Case는 상황·성분 아이디어를 찾고, 독립적으로 검수된 Evidence만 검증된 근거로 사용한다. 실제 제품 정보와 사용자 제약은 별도로 확인한다.
2. **방법 선택:** 충분한 문장은 원문을 유지하고, 첫 턴 키워드형 단편만 기존 intent 해석 LLM의 제한적 Case 질의 정리를 사용한다. 원하는 도움의 방향이 없는 첫 피부 고민 키워드는 Case 검색·재정렬 뒤 조건을 묻고, 제품 추천을 바로 실행하지 않는다. 검색은 Dense40, BGE 재정렬, Top-3이다. 자유형 재작성과 Case용 Hybrid는 기존 개발 질의에서 최종 전달 이득이 확인되지 않아 보류했다. 키워드형 정리의 이득은 아직 측정하지 않았다.
3. **현재 한계:** 신규 복합 질문 12건에서 관리 필터는 관련 Case가 있는 질의를 **12→10건**으로 줄였고, 관리 방향에 부합하는 사례 슬롯은 늘리지 못했다. 종합 질문 3건의 최종 답변도 모두 `partial`이었다. 같은 `gpt-4o-mini`에 Case 0건/Top-3만 달리 넣은 후속 8건 답변 진단에서도 Case 입력의 뚜렷한 답변 이득은 **0/8**, 사례 원문 인용은 **1/8**이었다. 따라서 **최종 추천 품질 개선이나 임상 안전성 향상은 아직 입증하지 않았다.**

발표의 성능 장표는 위 **방법 선택 비교 한 장**에 집중한다. 24건은 개발셋, 신규 복합 12건은 실패 유형을 바탕으로 만든 합성 도전셋, 종합 3건은 진단 실행이라고 각각 표기한다. 요약 질의·복수 질의·필터 실험의 수치는 질문을 받았을 때 설명하는 보조 자료로 둔다.

Case 입력 8건 비교는 발표에서 **현재 한계와 다음 개선 방향**을 설명할 때만 쓴다. 실제 운영의 Claim·Evidence·제품·루틴 조립까지 실행한 비교가 아니며, 실패 유형을 알고 고른 질의에 대한 단일 생성·Codex 판정이다. 결과가 말하는 것은 “유사 Case를 더 잘 찾는 것만으로 사용자 답변 개선이 증명되지 않았다”는 점이다. 아래 후속 기록에 질의별 판단과 원본을 남겼다.

### 실제 워크플로우로 연결 확인

같은 8개 질의를 실제 `ChatService`/LangGraph CLI에 **질의별 독립 세션**으로 넣었다. 운영 설정의 `gpt-4o-mini`, 실제 NIA Case·성분·제품 DB, BGE-M3 검색·BGE 재정렬을 사용했다. 이전의 Case 입력 답변 진단과 달리 **운영 Claim 추출·원문 검증·성분 ID·제품/루틴 경로**를 실행했다. [실행 기록](../../../tests/agent/nia_case_eval_data/nia_case_runtime_chain_results_20260927_v1.jsonl), [실행 코드](../../../tests/agent/evaluate_nia_case_runtime_chain.py)

이 실행은 **진단 CLI**이며 배포 HTTP 경로와 운영 저장소 검증은 아니다. 히스토리·체크포인터·루틴 저장은 개발용 메모리 구현을 쓴다. 8건은 이미 반복 사용한 개발 질의의 단일 실행이다.

| 실제 경로의 관찰 지표 | 8개 선택 질의 결과 | 의미 |
| --- | --- | --- |
| Case Top-3와 Claim 추출 | Top-3 **8/8**, `gpt-4o-mini` 추출 **8/8** | 검색에서 Claim 입력까지 흐름은 연결됐다. |
| Claim 원문 검증 | **50/68** 통과; 18건 제외 | exact quote 또는 인용문 속 성분명 검증에서 탈락했다. 통과는 효능·상황 적합성의 검증이 아니다. |
| 유효 Claim 성분의 표준 ID | **45/50** 연결 | 별칭 재조회 후에도 5건은 미연결됐다. |

특히 `completed`였던 T존 유분·볼 건조 질문에서도 최종 문장은 **얼굴 전체에 같은 모공 제품을 써도 되는지**에 직접 답하지 않았다. 면도 후 따가움·턱 여드름 질문과 턱 여드름·자국·따가운 볼 질문에는 레티놀 0.3 세럼이 루틴에 들어갔지만, 자극 부위와 사용 시점을 나누지 않았다. 필링 후 통증 질문의 루틴에는 보습 제품이 없고, “보습을 먼저 해야 하나”에도 답하지 않았다. 이는 현재 답변 조립과 조건 보존의 구체적 실패다. **발표에서는 검색 선택 근거와 이 종단 한계를 함께 제시하고, 최종 상담 품질 개선은 주장하지 않는다.** 아래 후속 기록에 질의별 결과를 적었다.

## 1. 무엇을 달성하려는가

사용자의 복합 피부 고민과 현재 상태를 읽고, **관련 사례 → 사례 속 성분 주장 → 검수 가능한 외부 근거 → 실제 제품과 사용 계획**을 연결해 선택 이유와 미확인 사항을 설명하는 것이 목표다. ### 실제 OpenAI API와 검색 평가의 경계

- 실제 워크플로우의 채팅 모델은 `gpt-4o-mini`다. 사용자 의도·경로 해석, 검색된 Case에서 관련 성분 Claim 선별, 근거 문장 생성 등 구조화된 판단 단계에 사용한다.
- Case 후보 검색과 재정렬은 이번 평가 기준으로 각각 BGE-M3와 `BAAI/bge-reranker-v2-m3`가 수행한다. Dense40과 Hybrid48 비교에서 `gpt-4o-mini`를 다시 호출하면 검색 방식 외 변수까지 바뀌므로 호출하지 않았다.
- 운영 LLM의 질의 처리 자체는 24개 질의에 실제 API를 24회 호출해 별도로 확인했다. LLM이 `query_plan.case_query` 초안을 만들지만, 최종 `IntentQueryPlanner`는 원문을 우선해 평가 대상 Case 질의 24개를 모두 원문과 같게 만들었다. [실제 API 실행](2026-09-26_1740_NIA_CASE_OPENAI_ROUTING_ONCE_REPORT.md), [결정적 경로 보정](2026-09-26_1755_NIA_CASE_ROUTE_UPDATE_REPORT.md)
- 자유형 질의 재작성 2×2 비교의 `gpt-4o-mini` 호출은 운영 질의 처리와 다른 실험용 재작성기다. 이 결과는 재작성 기능을 추가할지 판단하는 실험이며 현재 워크플로우 동작으로 설명하지 않는다.
- 이번 Hybrid Top-3에서 기존 qrel에 없던 4건은 OpenAI API가 아니라 현재 Codex 세션이 같은 0~3 기준으로 판정했다.

### Case 검색 방식에 관한 예상 질문

- **왜 현재는 Dense인가?** 운영 Case 경로는 BGE-M3 벡터 검색과 BGE 재정렬로 구현됐고 Case용 BM25 경로는 없다. 동일 가중치 RRF는 판정된 관련 Dense 후보를 밀어냈다. Dense 보존형 Hybrid40·Hybrid48은 후보 단계 qrel Recall을 0.648→0.683·0.720으로 올렸지만, 실제 전달하는 Top-3의 관련 사례 Hit는 Dense40 22/24, 두 Hybrid 모두 21/24였다. 순서는 부차적인 이 워크플로우에 맞춰 Top-5까지 넓혀 보니 세 방식 모두 Hit@5 22/24, 등급 3 Hit@5 19/24로 같았다. 평균 관련 사례 수@5는 Dense40 3.667, Hybrid40 3.708, Hybrid48 3.750으로 소폭 차이다. 후보·계약 비용까지 고려해 현재는 Dense40을 유지한다. [후보 구성 비교](2026-09-27_NIA_CASE_HYBRID_CANDIDATE_STRATEGY_REPORT.md), [Top-5 포함률](2026-09-27_NIA_CASE_TOP5_INCLUSION_REPORT.md)
- **질의 재작성은 어느 정도인가?** 운영 `IntentQueryPlanner`는 사용자 원문을 우선하고 상품·루틴 실행 지시만 제한적으로 제거한다. 별도 비교에서는 `gpt-4o-mini`가 증상·부위·상태·요청 방향을 보존하도록 한 개의 검색 질의로 재작성했다. 23/24 문장이 바뀌었지만 Dense Recall@40은 0.648→0.617, Hybrid는 0.685→0.648이었다. Dense 기준 2건 개선·4건 하락·18건 동일이고 API 지연은 평균 0.964초였다. 일부 문장에는 `유사 사례를 찾고 싶습니다`가 추가됐고, 필링 뒤 악화 같은 원인 문맥이 약해진 사례도 있었다. 현재 재작성 프롬프트는 채택하지 않는다. [2×2 비교](2026-09-27_NIA_CASE_REWRITE_HYBRID_2X2_REPORT.md)

### 주요 지표 해석

| 지표 | 이 문서에서 뜻하는 것 | 주의점 |
| --- | --- | --- |
| 후보 qrel Recall@K | 판정된 관련 사례 중 1차 후보 K건에 포함된 비율 | 3,581건 전체의 완전 Recall이 아니다. 다른 qrel 버전의 값은 직접 비교하지 않는다. |
| Hit@K | 질의 중 최종 K건에 등급 2~3 사례가 한 건 이상 있는 비율 | 1건만 있어도 성공이므로 사례의 충분한 개수와 복합 고민 충족은 알 수 없다. |
| 등급 3 Hit@K | 질의 중 최종 K건에 강한 관련 사례가 한 건 이상 있는 비율 | 사례 순서와 등급 3의 개수는 반영하지 않는다. |
| 평균 관련 사례 수@K · P@K | 질의당 등급 2~3 사례의 평균 개수 · K개 슬롯 중 관련 사례 비율 | K가 바뀌면 평균 개수는 늘고 P는 낮아질 수 있다. 같은 K끼리 비교한다. |
| nDCG@K | 0~3 관련도와 앞자리 우대를 함께 반영하는 순위 지표 | 사례의 **순서보다 포함**이 중요한 현재 Case 전달 판단에서는 보조 지표다. |

이 지표들은 Case 검색의 부분 지표다. 답변의 관리 조언 적합성, Claim 추출, 상품 연결 및 최종 추천 성공률을 대신하지 않는다.

## 4. 남은 시간이 적을 때의 발표 구성

1. **문제와 설계:** 복합 피부 상태에 맞는 제품·루틴을 출처와 함께 설명해야 한다 → 질의 해석, Case, Claim, Evidence, 제품·루틴으로 분리한다. Case는 탐색, Evidence는 검증이라는 출처 차이를 그림에 명시한다.
2. **선택 근거와 성능:** 복수 질의 폐기, 자유형 재작성 보류, Top-40 리랭크의 절충, 동일 가중치 RRF의 후보 손실을 한 장에 보여준다. Dense40·Hybrid40·Hybrid48의 **Hit@3→Hit@5와 평균 관련 사례 수@5**를 나란히 제시한다. Hybrid의 후보 Recall 이득이 실제 전달 사례의 성공 질의 수 증가로 이어지지 않았다는 점을 Dense40 유지 근거로 사용한다. nDCG와 요약 질의 비교는 보조로 둔다.
3. **현 상태와 다음 단계:** 신규 12건의 필터 역효과와 종합 3건의 `partial`을 보여주며, 현재 병목이 단순 검색 점수 외에도 복합 의도·관리 적합성·성분 연결·상품·근거 DB에 있음을 설명한다.

## 5. 다음 성능 개선 순서와 검증 기준

1. **지금은 새 질문셋 제작을 반복하지 않는다.** 기존 코퍼스 상대 24건에는 여러 관련 Case의 qrel이 있고 검색·필터 조정에 반복 사용됐으므로 개발·회귀셋이다. 별도 신규 복합 12건은 앞선 실패 유형에서 만든 합성 도전셋으로 필터 진단에 이미 사용됐다. 종합 3건도 오류 분석용이다. 새 12~20건을 만들면 결과 확인 전 고정했다는 차이는 있지만, 그것만으로 대표성·독립적인 최종 성능이 생기지 않는다. 시간이 부족하면 **기존 24건을 그대로 쌍별 방법 비교에 쓰고 결과를 개발셋 비교로 표기**한다. [24건 반복 개선](2026-09-27_NIA_CASE_CARE_COMPATIBILITY_UPDATE_REPORT.md), [복합 12건의 성격](2026-09-27_NIA_CASE_FRESH_COMPOSITE_CHALLENGE_REPORT.md)
2. **복합 고민의 소실 위치를 계측한다.** 고민별 관련 사례가 코퍼스에 있는지, Dense Top-40에 있는지, rerank Top-3/5에 남는지 따로 기록한다. 면도 자극은 재정렬에서, 색소+주름 질문의 보조 고민은 1차 후보에서 빠졌다는 기존 관찰을 기준 사례로 쓴다. 후보 다양화나 질의 변경은 같은 고정셋에서 Hit@K·등급 3 Hit@K·관련 사례 수@K·복합 조건 커버리지를 우선 비교한다.
3. **조건 적합성을 Case에서 최종 출력까지 확인한다.** 현재 자극·회복 우선 요청과 충돌하는 Case 권고뿐 아니라 상품 목록과 최종 문장도 판정한다. 출력률·관련성·부합/충돌 노출을 함께 보고, 필터가 결과를 비우는 비용을 숨기지 않는다. 표현 목록 확장만으로 해결됐다고 보지 않는다.
4. **연결 단계의 실패를 줄인다.** 성분별 `Claim 원문 인용 유효율 → 표준 ID 해소율 → 제품 조회 성공률 → 요청한 루틴 완수율`을 질문별로 기록한다. 기존 3건의 `ingredient_ids=[]`, 성분 별칭 불일치, `routine_planning` 미완수를 우선 재현한다. 이는 Case 검색의 정밀도와 다른 병목이다.
5. **Evidence DB 검수 계약이 정해진 뒤 두 번째 층을 평가한다.** 검수 상태의 실제 DB 값과 Agent 매핑을 소유 파트와 합의하고, 원문 출처·성분·적용 조건이 판정된 소규모 근거셋을 만든다. 그 뒤 Citation 정확도·`SUPPORTED` 판정 정밀도·근거 부족 시 보류율을 측정한다. 지금은 Evidence 수치를 만들어 발표하지 않는다.

**완료한 최소 비교:** 원문 Dense40과 Hybrid48·Hybrid40을 동일 BGE reranker로 Top-3와 오프라인 Top-5까지 비교했다. 두 Hybrid 안 모두 후보 Recall은 높였고 Top-5 관련 사례 수는 소폭 늘었지만 Hit@5와 등급 3 Hit@5는 Dense와 같았다. 현재 운영 구현은 Dense40·Top-3을 유지한다. 다음 비교는 같은 실제 워크플로우 LLM·같은 답변 지시·같은 질문에서 입력 Case 자료만 `없음`과 `Dense40에서 선택한 Top-3`로 바꾸어 Case 단계 답변의 필수 질문 충족, 현재 상태와 충돌하는 조언, 원문 추적 가능성을 쌍별로 판정하는 것이다.

시간이 매우 제한되면 **새 알고리즘 추가보다 쌍별 방법 비교와 위 2~4의 단계별 오류 기록을 먼저 완성**한다. 최종 지표는 “사용자가 요청한 핵심 과제를 근거와 함께 충족한 질의 비율”로 두고, Case 관련성·조언 적합성·성분 연결·근거 상태를 실패 원인을 찾는 하위 지표로 사용한다. 나중에 일반화 가능한 수치가 필요하면 개발셋을 다시 쓰지 않고 미사용 사용자형 질문을 별도로 수집·판정한다.

### 이 결과로 바꾸는 판단

Dense40·Top-3는 여전히 **관련 사례를 찾는 기본 경로**로 유지한다. 다만 이 실험은 “관련 사례를 넣으면 답변이 좋아진다”는 발표 주장을 뒷받침하지 못했다. Case의 의도한 기여는 사례 답변을 통째로 답변 모델에 넣는 데 있지 않고, **질문에 맞는 성분 Claim을 원문 그대로 추출·검증한 다음 조건과 출처를 보존해 다음 단계에 전달하는 것**이다. 따라서 다음 개선·평가는 Hybrid나 Top-5 확장보다 `Case → exact quote Claim → 표준 성분 ID → 제품·루틴` 연결의 유효율과 복합 조건 보존을 우선한다. 사례 답변의 성분 주장을 독립적으로 검증된 효능 근거처럼 제시하지 않는다.
