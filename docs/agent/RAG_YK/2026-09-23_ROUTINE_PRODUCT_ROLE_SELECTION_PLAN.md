# 역할 기반 상품 추천·결정적 루틴 생성 계획

- 작성일: 2026-09-23 KST
- 최종 갱신: 2026-09-23 KST
- 상태: **Agent 구현 및 회귀 테스트 완료**
- 범위: `agent/`, `tests/agent/`, Agent 문서
- 관련 문서: [LLM Routine Rule 생성·결정적 검증 구현](2026-09-21_1404_LLM_ROUTINE_RULE_IMPLEMENTATION.md)

## 1. 문제

피부 고민에서 선별한 추천 성분으로 상품 여러 건을 정상 조회해도,
`RecommendationProductSelector`가 추천 성분을 모두 포함한 한 제품만 남길 수 있다. 이 제품이
클렌저라면 `RoutineProductSelector`와 LLM Routine Planner는 클렌저 하나만 입력받고, 기간에 맞춰
같은 클렌저를 반복 배치한 루틴을 만들 수 있다.

현재 단계별 목적은 다음처럼 어긋나 있다.

```text
추천 상품 선택: 추천 성분을 최소 상품 수로 덮음
루틴 상품 선택: 이미 축소된 후보 안에서 역할별 첫 제품을 선택함
LLM 루틴 생성: 전달된 제품으로 일정 전체를 자유 생성함
결정적 검증: 입력 제품 누락은 막지만 근거 없는 반복을 충분히 막지 못함
```

성분 집합을 최소 상품 수로 덮는 것은 상품 수를 줄이는 문제에는 맞지만, 역할이 다른 상품을
보여주고 사용 순서를 구성해야 하는 루틴에는 맞지 않는다.

## 2. 확정 정책

### 2.1 상품 검색은 한 번만 실행한다

- 최초 성분 기반 상품 검색 결과를 전체 후보 풀로 보존한다.
- 역할이 누락돼도 카테고리별 보완 검색을 실행하지 않는다.
- 추천 성분 조건을 제거한 카테고리 단독 검색도 실행하지 않는다.
- 같은 조건으로 재검색하는 fallback을 만들지 않는다.

따라서 상품 후보 구성 때문에 Backend `ProductRepository` 조회 계약이나 SQL을 바꾸지 않는다.

### 2.2 검색된 상품을 역할별로 모두 보여준다

검색된 상품을 다음 상위 역할로 분류한다.

| 역할 | 의미 | 현재 예상 카테고리 예시 |
| --- | --- | --- |
| `CARE` | 피부 고민을 겨냥한 선택 단계 | 토너·패드, 에센스·세럼, 앰플 |
| `MOISTURIZE` | 보습·마무리 단계 | 크림·로션 |
| `CLEANSE` | 세정 단계 | 클렌저 |
| `UNCLASSIFIED` | 현재 정보로 역할을 확정하지 못함 | 기타, 판매처명이 카테고리로 들어온 상품 |

- 역할별 대표 한 개만 상품 후보로 보여주지 않는다. 최초 검색 풀에 포함된 후보를 역할별 목록으로
  모두 보여준다.
- 원래 `ProductCategory`와 검색 순위를 보존한다.
- 같은 상품은 `product_id` 기준으로 한 번만 노출한다.
- 지원 Taxonomy로 분류할 수 없는 상품을 상품명만 보고 임의 역할로 확정하지 않는다.

### 2.3 추천 표시 순서와 실제 사용 순서를 분리한다

추천 후보의 표시 우선순위는 다음과 같다.

```text
케어 → 보습 → 세안 → 미분류
```

같은 시간대의 실제 사용 순서는 다음과 같다.

```text
세안 → 케어 또는 특수 케어 → 보습
```

케어 우선은 서비스의 상품 제시 정책이다. 카테고리만으로 케어 제품의 효능이 세안제보다 높다고
입증하는 것은 아니므로 사용자 응답에서 효능 우위로 표현하지 않는다.

### 2.4 루틴 생성 시 역할별 대표 상품을 한 개 선택한다

상품 후보 화면에는 역할별 후보를 모두 보여주되, 루틴 생성에는 각 기본 역할에서 대표 상품을
최대 한 개만 사용한다.

같은 역할 안의 대표 상품은 다음 사전식 순서로 선택한다.

1. 더 높은 성분 근거 수준
2. 사용자가 명시한 상품 조건 충족
3. 일반적인 해당 역할에 사용할 수 있는 제품인지
4. 더 많은 추천 성분 연결
5. 최초 DB 검색 순위
6. 안정적인 상품 ID 순서

각 기준을 임의 가중치로 합산하지 않는다. 앞 기준이 같을 때만 다음 기준을 비교해야 근거 부족이나
역할 부적합을 단순 성분 개수로 상쇄하지 않는다.

### 2.5 후보가 없는 역할은 미확정 슬롯으로 남긴다

후보가 없는 역할을 다른 역할의 상품으로 채우거나 가짜 상품으로 생성하지 않는다. 루틴 구조에는
제품이 아직 정해지지 않은 역할 슬롯을 남긴다.

```text
3. 보습 — (보습 상품: 이번 검색 결과에서 후보 없음)
```

최초 검색은 DB 전체를 확인한 검색이 아니라 제한된 후보 검색이므로 `보습 제품이 없습니다`처럼
DB 전체에 제품이 없다는 의미로 확대하지 않는다.

미확정 슬롯은 실제 `ProductRecord`나 `RoutinePlacement`가 아니다. 가짜 `product_id`를 만들지
않고 역할, 누락 상태, 표시 문구를 가진 별도 Pydantic 모델로 표현한다.

### 2.6 미분류 상품은 자동으로 한 번 배치하지 않는다

`UNCLASSIFIED`는 빈 자리를 채우는 추가 상품 역할이 아니다. 1회 제한은 빈도만 줄일 뿐 제품의
역할·순서·시간대가 불명확한 문제를 해결하지 못한다.

다음 조건을 모두 만족한 상품만 `SPECIAL_CARE`로 승격할 수 있다.

- 제품 공식 사용법 또는 검수된 출처에서 적용 가능한 Routine Rule을 확인함
- 배치 가능한 시간대·순서·횟수를 결정할 수 있음
- 이미 선택된 케어 상품과의 충돌이 없음
- 사용자 제외 조건에 해당하지 않음
- 세안이나 보습 역할을 대체하지 않음

`SPECIAL_CARE` 정책은 다음과 같다.

- 전체 루틴에서 최대 한 개 상품
- 전체 생성 기간에서 총 한 번만 배치
- 일반 케어 상품과 충돌하면 일반 케어 또는 특수 케어 중 하나만 배치
- Rule이 없는 미분류 상품은 후보 목록에만 표시하고 자동 루틴에서 제외

## 3. 선택·생성 방법론

### 3.1 상품은 역할 층화 선택으로 결정한다

최종 루틴 상품 선택에는 기존 최소 Set Cover를 사용하지 않는다. 한 번 조회한 상품 풀을 역할별로
나누는 **역할 층화 선택(role-stratified selection)**을 사용한다.

```text
성분 기반 상품 검색 1회
  → 전체 검색 풀 보존
  → ProductCategory를 상위 역할로 매핑
  → 역할별 후보 전체 표시
  → 기본 역할별 대표 상품 최대 한 개 선택
  → Rule이 확인된 미분류 상품만 특수 케어 후보로 승격
  → 결정적 Routine Scheduler에 전달
```

최소 Set Cover는 역할이 다른 상품을 제거하므로 최종 후보 선택에 사용하지 않는다.

### 3.2 일정은 결정적 Rule Scheduler가 만든다

LLM이 일정 전체를 자유 생성하지 않는다. 일정은 검증된 Rule과 명시적인 서비스 정책을 적용하는
결정적 Scheduler가 생성한다.

Rule 적용 우선순위는 다음과 같다.

1. 사용자의 명시적 제약
2. 제품 공식 사용법에서 검증한 `REQUIRED` Rule
3. 검수된 Evidence에서 검증한 `REQUIRED` Rule
4. 서비스의 기본 역할 순서

미검수 Evidence와 Case 사용 가이드는 `WARNING`으로만 사용한다. 경고만으로 시간대나 빈도를
새로 만들지 않는다. 제품명에 `레티놀`, `레티날`, `필링` 같은 단어가 있다는 이유만으로 저녁
배치를 확정하지 않는다.

### 3.3 LLM의 책임을 제한한다

LLM은 다음 역할만 맡는다.

- 사용자 요청에서 기간·횟수·명시 시간대·제외 조건을 구조화
- 제품 사용법과 Evidence에서 출처가 있는 Routine Rule 후보 추출
- 결정된 루틴의 사용자용 설명 생성

코드는 다음을 결정한다.

- 상품 역할과 미분류 상태
- 역할별 대표 상품
- 미확정 역할 슬롯
- Rule의 출처·exact quote·적용 제품 검증
- 루틴 순서·횟수·시간대·충돌 처리
- 특수 케어의 총 1회 제한

LLM이 역할 분류, 상품 ID 생성, 검색 조건 완화, 누락 역할 대체 또는 최종 배치를 결정하지 않는다.

## 4. 기간과 횟수 표현

사용자가 실제 요일을 말하지 않았다면 월요일·화요일 같은 요일을 임의로 생성하지 않는다.

| 사용자 표현 | 내부 의미 | 사용자 표시 |
| --- | --- | --- |
| `3일간 루틴` | 3일 범위 | `1일차`, `2일차`, `3일차` |
| `5일 루틴` | 5일 범위 | `1일차`부터 `5일차` |
| `루틴 3회` | 총 3개 실행 슬롯 | `루틴 1`, `루틴 2`, `루틴 3` |
| `주 3회` | 7일 범위의 최대 또는 목표 3회 | `주간 루틴 1~3` |
| `월·수·금` | 명시 요일 | `월요일`, `수요일`, `금요일` |

- 단독 `N회`를 `주 N회`로 해석하지 않는다.
- `N일`과 `N일간`을 같은 기간 표현으로 해석하되 `주 N일`을 기간으로 중복 해석하지 않는다.
- `N일간`을 매일 아침·저녁 총 `2N회`로 확대하지 않는다.
- 아침·저녁은 사용자가 명시하거나 검증된 `ALLOWED_PERIOD` Rule이 있을 때만 붙인다.
- 시간대를 결정할 근거가 없으면 임의로 저녁을 선택하지 않고 `미지정` 상태를 보존한다.

## 5. 상태와 타입 경계

검색 결과, 실제 상품 배치, 미확정 역할을 구분한다.

```text
검색 풀
  최초 상품 검색에서 반환된 전체 ProductRecord

역할별 후보
  검색 풀을 CARE/MOISTURIZE/CLEANSE/UNCLASSIFIED로 나눈 결과

선택 상품
  기본 역할별 대표 상품과 승인된 SPECIAL_CARE 상품

실제 배치
  product_id가 있는 제품의 결정적 일정 배치

미확정 역할 슬롯
  product_id 없이 role과 missing 상태만 가진 표시용 슬롯
```

권장 타입은 모두 Enum과 Pydantic 모델로 정의한다.

- `RoutineProductRole`: `CARE`, `MOISTURIZE`, `CLEANSE`, `SPECIAL_CARE`, `UNCLASSIFIED`
- `RoutineRoleCandidateGroup`: 역할과 해당 상품 후보 목록
- `RoutineProductSelectionResult`: 역할별 대표 상품, 미분류 상품, 누락 역할
- `RoutineRoleSlotStatus`: `SELECTED`, `MISSING_CANDIDATE`, `OMITTED`
- `RoutineRoleSlot`: 역할, 상태, 선택 상품 참조 또는 누락 표시
- `RoutineSequenceKind`: `DAY`, `OCCURRENCE`, `WEEKLY_OCCURRENCE`, `EXPLICIT_WEEKDAY`

현재 `RoutinePlan`은 `Weekday`, `DayPeriod`, 필수 `product_id`를 가진 `RoutinePlacement` 중심이다.
번호 기반 순서와 미확정 역할 슬롯을 공개 Artifact에 포함하면 `RoutinePlan` 계약이 바뀐다. 이는
Backend 저장과 Front 표시에도 영향을 줄 수 있으므로 구현 전에 `docs/contracts/backend-to-agent.md`
및 필요 시 `docs/contracts/front-to-backend.md` 변경 초안을 먼저 작성하고 상대 파트와 합의해야 한다.

## 6. 응답 예시

### 6.1 역할별 상품 후보

```text
추천 상품

케어 후보
1. 넘버즈인 No.9 NAD Bio Lifting-sil 에센스 50ml
2. Arencia 레드 Smoothie 세럼 8 30ml
3. 토리든 Cellmazing 모공 Perfecting 앰플 30ml
4. athe 토닝 Vita EGF 세럼 30mL

보습 후보
1. SKINFOOD Royal 꿀 모이스처 크림 100mL
2. 아누아 레티놀 0.1 카페인 리바이탈라이징 아이크림 30g
3. 토리든 Cellmazing 퍼밍 크림 60mL

세안 후보
1. AROCELL 슈퍼 콜라겐 앰플 팩 To 폼 클렌저 120g

미분류 후보
1. Arencia 레티날 부스터 샷 30ml
2. 디오디너리 알로에 2% + NAG 2% 솔루션 30mL
```

### 6.2 후보가 모두 있는 번호 기반 루틴

```text
루틴 1
1. 세안 — AROCELL 슈퍼 콜라겐 앰플 팩 To 폼 클렌저
2. 케어 — 넘버즈인 No.9 NAD Bio Lifting-sil 에센스
3. 보습 — SKINFOOD Royal 꿀 모이스처 크림
```

### 6.3 후보가 없는 역할

```text
루틴 1
1. 세안 — 선택된 클렌저
2. 케어 — 선택된 세럼
3. 보습 — (보습 상품: 이번 검색 결과에서 후보 없음)
```

### 6.4 검증된 특수 케어가 있는 3회 루틴

```text
루틴 1
1. 세안 — 선택된 클렌저
2. 케어 — 선택된 세럼
3. 보습 — 선택된 보습제

루틴 2
1. 세안 — 선택된 클렌저
2. 특수 케어 — 검증된 미분류 상품
3. 보습 — 선택된 보습제

루틴 3
1. 세안 — 선택된 클렌저
2. 케어 — 선택된 세럼
3. 보습 — 선택된 보습제
```

특수 케어의 공식 사용법 또는 검수된 Rule이 없으면 위 두 번째 배치를 생성하지 않고 미분류 후보에만
남긴다.

## 7. 구현 결정

1. 아이크림·선크림·마스크·팩은 넓은 상위 카테고리가 `크림·로션`이어도 기본 보습 대표로
   자동 선택하지 않는다. 현재 Product DTO에 세부 용도 필드가 없으므로 상품명은 역할 부여가 아닌
   보수적 제외 신호로만 사용한다.
2. `CLAIM_ONLY` 상품은 후보와 역할 대표 선택에는 남기되 Claim 한계를 함께 표시한다. Claim 자체는
   특별 케어 일정 Rule이나 안전성 근거로 사용하지 않는다.
3. 제품별 빈도 Rule이 없으면 선택된 기본 세안·케어·보습 대표를 사용자가 요청한 번호 슬롯마다
   반복한다. 검증된 최대 빈도 Rule이 있으면 Rule이 반복 정책보다 우선한다.
4. 자외선 차단은 이번 범위에서 기본 역할로 확장하지 않고 미분류로 둔다. 아침 루틴 필수 단계로
   자동 생성하지 않는다.
5. 번호와 누락 역할 문구는 Agent 응답에서 조립한다. 공개 `RoutinePlan`의 기존 `weekday`는 저장
   호환을 위한 내부 순서 키로 유지하고, 단독 횟수와 시간대 미지정을 구분하는
   `occurrence_count`, `DayPeriod.UNSPECIFIED`만 추가했다.

## 9. 필수 회귀 시나리오

1. 한 클렌저가 추천 성분을 모두 포함해도 케어·보습 후보가 제거되지 않는다.
2. 역할별 후보 목록에 최초 검색 풀의 상품이 중복 없이 보존된다.
3. 추천 후보 표시 순서는 케어·보습·세안·미분류다.
4. 루틴에는 기본 역할별 대표 상품이 최대 한 개만 선택된다.
5. 같은 시간대의 사용 순서는 세안·케어 또는 특수 케어·보습이다.
6. 후보가 없는 역할은 가짜 `product_id` 없이 미확정 역할 슬롯으로 표시된다.
7. 누락된 역할 때문에 추가 상품 검색이 실행되지 않는다.
8. Rule이 없는 미분류 상품은 자동 루틴에서 제외된다.
9. Rule이 확인된 특수 케어는 전체 루틴에서 한 상품·한 배치만 허용된다.
10. 특수 케어와 일반 케어가 충돌하면 둘을 같은 슬롯에 배치하지 않는다.
11. `3일간`은 `1일차~3일차`, 단독 `3회`는 `루틴 1~3`으로 표시된다.
12. 명시하지 않은 요일이나 아침·저녁을 임의 생성하지 않는다.
13. 사용자가 거절한 후보는 역할 목록의 선택 대상과 루틴에서 모두 제외된다.
14. 분류할 수 없는 상품을 이름만 보고 기본 역할에 넣지 않는다.
15. 사용자에게 표시되지 않은 실제 상품이 루틴에 배치되지 않는다.

## 10. 완료 조건

- 최초 상품 검색 결과가 역할 분류 전까지 보존된다.
- 역할별 후보 전체와 루틴용 대표 상품이 구분된다.
- 최소 Set Cover가 서로 다른 루틴 역할의 후보를 제거하지 않는다.
- 케어 우선 추천과 세안 우선 사용 순서가 독립적으로 적용된다.
- 누락 역할이 미확정 역할 슬롯으로 표시되고 다른 상품으로 대체되지 않는다.
- 보완 검색이나 조건 완화가 발생하지 않는다.
- 검증된 Rule이 없는 미분류 상품은 루틴에 들어가지 않는다.
- 특수 케어는 검증된 Rule 아래에서 전체 계획에 총 한 번만 배치된다.
- 기간과 횟수는 실제 요일이 아닌 번호로 표현되고, 명시되지 않은 시간대를 만들지 않는다.
- LLM은 요청·Rule 추출·설명만 담당하고, 최종 일정은 결정적 Scheduler와 Validator가 확정한다.
- 공개 Artifact의 호환 필드는 Backend→Agent 계약 문서와 코드가 일치한다.
