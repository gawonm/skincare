# 1차 RAG 단계 Query Rewriting 성능 개선 가능성 및 기술 분석 보고서

> **평가 기준 일자**: 2026-09-27
> **대상 도메인 및 코퍼스**: 한국어 임상/스킨케어 NIA Case 3,581건 (`nia_case_text/v1`, BGE-M3 Dense + BM25 Hybrid)
> **핵심 결론**: **"단일 턴 질의의 자유형 LLM 재작성은 1차 검색 성능을 오히려 떨어뜨리는 독(Poison)이지만, '태스크 지시어 제거', '멀티턴 문맥 복원', '복합 고민 축별 보존 분해'는 필수적이자 유일한 유효 경로이다."**

## 1. Executive Summary (핵심 요약)

"Query Rewriting으로 1차 RAG 검색 성능을 끌어올릴 수 있는가? 가능성이 있는가?"라는 질문에 대한 결론은 다음과 같습니다.

1. **단순 LLM 문장 재작성(Paraphrasing)은 실패하며, 성능을 하락시킵니다.**
   - 실제 프로젝트 벤치마크 결과, `gpt-4o-mini` 단일 질의 재작성은 BGE-M3 Dense Recall@40을 **0.648에서 0.617로 하락(-3.1%p)**시켰습니다.
   - 검색 지연 시간은 DB 벡터 검색(0.081초) 대비 **12배 증가한 0.964초**가 소요되었습니다.
2. **실패의 근본 원인**:
   - **메타 토큰 오염**: LLM이 `~경우의 유사 사례를 찾고 싶습니다` 같은 공손한 검색 목적어를 붙여 문장 전체 임베딩 중심점을 교란 (24개 중 11개 질의 오염).
   - **임상적 인과 관계 소실**: 질의를 다듬는 과정에서 "필링을 자주 했더니" 같은 핵심 유발 요인을 삭제하여 특정 질의에서 Recall이 **1.000 → 0.400으로 폭락**.
   - **교집합 조건 파괴**: 질의를 하위 요소(나이/성별 vs 고민)로 분해 후 RRF하는 Multi-query 방식은 **Hit@20을 91.7%에서 50.0%로 반토막** 냈습니다.
3. **그렇다면 Query Transformation의 진짜 가능성은 어디에 있는가?**
   - **[유효 1] 태스크 지시어 노이즈 분리 (Instruction Stripping)**: 사용자 원문의 피부 고민·상태는 100% 보존하고, 검색과 무관한 "루틴 짜줘", "제품 추천해줘"만 결정적 규칙(Regex/AST)으로 제거 (현재 `IntentQueryPlanner` 구현, Hit@20 **91.7%** 달성).
   - **[유효 2] 멀티턴 대화 맥락 복원 (Multi-turn Resolution)**: 후속 턴의 단답형 질문("그럼 각질 제거는?")에 이전 턴의 나이/피부타입/고민을 주입하는 재작성은 **선택이 아닌 필수(0% → 80%대 복구)**.
   - **[유효 3] 복합 고민 축별 양자 보존 분해 (Aspect-Preserving Dual-Path Retrieval)**: T존 모공과 볼 건조가 상충하는 복합 질의의 경우, 두 축의 독립 쿼터(각 Top-20)를 확보한 뒤 리랭커에 전달.
   - **[효율적 대안] Dense 확장보다 BM25 Sparse Hybrid 도입이 80배 빠르고 확실한 개선**: 원문 Hybrid(Dense+BM25) 도입 시 **Recall@40이 0.648 → 0.685로 즉각 상승(+3.7%p)**, 소요 시간은 단 **0.011초(11ms)**.

## 3. 심층 실패 원인 분석: 왜 일반적인 Query Rewriting이 망가지는가?

### 원인 1: 메타 텍스트 오염 (Meta-Linguistic Noise Injection)
LLM에게 "검색을 위해 한 문장으로 재작성하라"고 지시했을 때, 프롬프트의 지시어에 반응하여 문장 끝에 전형적인 완곡어구를 자동으로 삽입했습니다.
- 원문: `"여드름이 나았는데 볼에 갈색 자국이 오래 남아 있습니다."` (29자)
- 재작성: `"여드름 후 볼에 갈색 자국이 오래 남아 있는 경우의 유사 사례를 찾고 싶습니다."` (47자)
- 결과: **Recall@40이 0.500에서 0.250으로 반토막**.
- **원리적 이유**: BGE-M3 Dense 임베딩은 전체 문장의 토큰 임베딩을 평균(Mean-pooling)합니다. 29자 핵심 증상에 24자짜리 "경우의 유사 사례를 찾고 싶습니다"가 추가되면서, 벡터의 절반 가까운 가중치가 스킨케어 도메인과 무관한 일반 서술어 쪽으로 끌려갔습니다.

### 원인 2: 핵심 인과 관계 및 촉발 요인 소실 (Causal Trigger Erasure)
`evaluation_core_pigment_08` 케이스:
- 원문: `"기미에 좋다는 필링을 자주 했더니 건조하고 따가워졌습니다. 색소와 장벽을 같이 회복하고 싶어요."`
- 재작성: `"기미로 인해 건조하고 따가운 피부를 가진 경우 색소와 장벽을 동시에 회복할 수 있는 스킨케어 제품을 찾고 싶습니다."`
- 손실: **Recall@40이 1.000에서 0.400으로 60%p 폭락**.
- **치명적 오류**: 환자의 장벽 손상과 따가움의 원인은 **"필링(화학적 각질제거)을 자주 해서"** 발생한 접촉성 장벽 손상입니다. 기미 자체는 따가움을 유발하지 않습니다. LLM은 문장을 매끄럽게 만든답시고 핵심 촉발 요인인 `"필링을 자주 했더니"`를 통째로 지워버렸고, 결과적으로 "각질제거 시술 후 장벽 회복" 관련 정답 Case들을 완전히 놓치게 되었습니다.

### 원인 3: Dense 임베딩의 '단어 추가 역효과' (Centroid Drift)
흔히 생각하기에 "동의어나 의학 용어를 쿼리에 덧붙이면 Dense 검색이 잘 되겠지?"라고 생각하지만, 실측 결과(Cond 4) Recall은 **0.648 → 0.610으로 하락**했습니다.
- 사용자가 `"코에 블랙헤드가 반복되고 모공이 막혀 보여요"`라고 했을 때 임상 키워드 `"피지 각질 정돈 BHA 나이아신아마이드"`를 덧붙이면:
- 쿼리 벡터가 코퍼스 내 3,581개 중 흔하디흔한 "BHA 피지 조절 화장품 질문" 수천 개 쪽으로 강하게 끌려갑니다.
- 그 결과, 사용자의 구체적 조건(자극 없이 관리, 코 부위 집중)을 만족하는 고품질 정답 문서들이 상위 40위 밖으로 밀려나는 **Centroid Drift(군집 중심 이동)**가 발생합니다.

## 5. Query Rewriting으로 1차 RAG를 진짜 끌어올리는 3가지 유효 방법

### 방법 1: 태스크 지시어 노이즈 분리 (Instruction De-noising) — [규칙 기반]
사용자가 입력하는 문장에는 **"정보 검색 신호(증상, 피부타입, 환경)"**와 **"에이전트 행동 지시(추천 요청, 루틴 요청, 포맷)"**가 뒤섞여 있습니다.

```text
[사용자 입력]
"30살 남성이고 면도 후 턱에 여드름과 따가움이 반복됩니다.
 올리브영에서 살 수 있는 순한 세럼 3개 추천해주시고 일주일 루틴 짜주세요."
```
- NIA 코퍼스의 3,581개 케이스 문서에는 "올리브영", "세럼 3개", "일주일 루틴"이라는 단어가 없습니다. 이 단어들이 쿼리에 들어가면 임베딩 벡터가 상업적/스케줄링 어휘 쪽으로 오염됩니다.
- **해결책**: 현재 `agent/query_planning.py`의 `IntentQueryPlanner`가 수행하는 것처럼, LLM 호출 없이 정규식 및 문법 패턴으로 행동 지시어를 제거하고 순수 임상 상태문만 남깁니다:
  - `case_query`: `"30살 남성이고 면도 후 턱에 여드름과 따가움이 반복됩니다."`
- **효과**: Hit@20 **91.7%**, 레이턴시 **0.000초**, API 비용 **$0**.

### 방법 2: 멀티턴 대화 맥락 복원 (Conversational Query Rewriting) — [LLM 필수]
단일 턴 평가(골든셋 24건)에서는 사용자가 처음부터 풍부한 정보를 제공하므로 재작성이 독이 되지만, **실제 대화형 챗봇의 2번째 턴 이후에서는 Query Rewriting이 성능의 생명선**입니다.

- **핵심 규칙**:
  - LLM에게 "문장을 멋지게 바꿔라"고 하지 말고, **"이전 대화에서 확정된 사용자 프로필(나이, 피부타입)과 선행 고민을 생략된 의문문에 주입하여 완결된 단독 문장으로 만들어라"**는 단일 제약만 부여합니다.
  - 예: Turn 1 ("20대 지성 좁쌀 여드름") → Turn 2 ("각질 제거는 어떻게 해?") → 생성 질의: `"20대 지성 이마 좁쌀 여드름 피부의 각질 제거 방법"`

### 방법 3: 복합 고민 축별 보존 분해 (Aspect-Preserving Dual-Path Retrieval)
복합 고민 질의(`evaluation_core_composite_01`: "T존 모공/피지는 심한데 볼은 붉고 건조합니다")는 두 피부 부위의 요구사항이 정반대입니다.
- 단일 쿼리로 검색하면 피지/모공 케이스만 상위 40개를 다 차지하거나, 홍조/건조 케이스만 차지하여 나머지 한 축의 정답이 탈락합니다.
- **아키텍처 제안**:
  1. 복합 질의를 축별로 나눕니다 (축 A: "T존 모공 피지 복합성", 축 B: "볼 건조 붉은기 장벽 복합성").
  2. 축 A로 Top-20, 축 B로 Top-20을 각각 병렬 Dense 검색합니다.
  3. 두 리스트를 합쳐 중복을 제거하고 총 30~40개의 후보 풀을 만듭니다.
  4. 후속 교차 인코더(BGE Reranker)에게 "두 축의 균형 있는 고려"를 평가하도록 넘깁니다.

## 6. 대안 전략: Query Rewriting보다 훨씬 빠르고 확실한 1차 검색 개선책

Query Rewriting에 LLM API를 쓰는 것(1초 지연, 월 수십만원 비용, 불안정한 임베딩)보다, **검색 인덱스 구조와 하이브리드 파이프라인을 개선하는 것이 비용 대비 효과가 압도적**입니다.

### 1) BM25 Lexical + BGE-M3 Dense 하이브리드 융합 (RRF)
- 원문 Dense 단독 Recall@40: **0.648**
- 원문 Dense + BM25 RRF Recall@40: **0.685 (+3.7%p 개선, 10개 질의 승리)**
- 추가 시간: **0.011초 (11ms)** (메모리 BM25 역색인 검색)
- LLM 재작성은 1,000ms를 쓰고도 성능을 깎아먹었지만, BM25 결합은 11ms만에 성능을 끌어올립니다.

### 2) 인덱스 적재 비대칭 해소 (Ingestion Chunking Alignment)
- 현재 쿼리는 40자인데, 문서 `embedding_text`는 `[질문] + [답변] + [추론]` 합쳐서 2,000자에 육박합니다.
- 사용자가 질문을 던질 때 2,000자짜리 방대한 답변+추론 텍스트와 코사인 유사도를 계산하므로 비대칭성(Asymmetry) 손실이 발생합니다.
- **해결책**: 문서를 적재할 때 `[질문]` 전용 임베딩 인덱스를 별도로 두고 다중 벡터 검색을 지원하면, 런타임 LLM 재작성 비용 없이도 질의-문서 간 길이 및 어휘 비대칭을 100% 해소할 수 있습니다.

## 7. 최종 결론 및 권고 사항

1. **"1차 RAG에서 단순 프롬프트 재작성으로 성능을 끌어올릴 수 있는가?"**
   - **불가능하며, 오히려 손해입니다.** 한국어 임베딩 모델(BGE-M3) 환경에서 LLM의 자유형 재작성은 메타 노이즈 주입과 세부 인과 삭제로 인해 검색 재현율을 유의미하게 하락시킵니다.
2. **"그렇다면 어디에 구현해야 하는가?"**
   - **멀티턴 대화 복원**: 후속 턴에서 생략된 문맥을 채우는 쿼리 리라이팅에만 LLM을 투입하십시오.
   - **태스크 지시어 제거**: 원문 증상은 손대지 않고 "추천해줘/루틴짜줘"만 정규식으로 지우는 현재의 `IntentQueryPlanner` 정책을 유지하십시오.
3. **"1차 단계 Recall을 추가로 올리려면 무엇을 해야 하는가?"**
   - 질의를 억지로 고치려 하지 말고, **원문 질의에 대한 BM25 하이브리드(RRF) 검색을 공식 채택**하는 것이 가장 확실하고 비용 효율적인 방법입니다.
